# Service 审查与待办

更新日期：2026-10-29。

当前设计的主干合理：单事件循环处理请求，同步读写文件，使用内存元数据表并持久化到 JSON，符合 Linux 服务端第一版小文件存储的目标。主要路径已有真实 HTTP 测试，但配置组合和应用级闭环仍有缺口。

本文整理前期 Service 审查结论，并按当前源码和已有回归测试更新状态。保留原审查的六项编号，前三项已完成；后续逐项解决时同步更新状态和验收记录。

### 1.1 默认存储目录末尾分隔符

- [x] 修复目录比较并增加回归测试。

**原问题：** `Download()` 直接比较配置目录和元数据文件的父目录。默认目录保留末尾 `/`，导致比较不相等，两种策略均出现上传 201、下载 500。

**当前实现：** 将配置目录与文件名组合，调用 `lexically_normal()` 后与元数据中的完整文件路径比较，兼容末尾分隔符。

**已有验收：** `DownloadsWithTrailingSeparatorsInConfiguredStorageDirectories` 覆盖带末尾 `/` 的相对、绝对目录，以及普通、压缩两种策略；上传后下载内容一致，重建 Service 后仍可下载。该测试覆盖默认配置的路径写法，尚不能代替默认配置下的完整应用启动验收。

修复提交：`fc8c5bd`。

### 1.2 请求回调异常边界

- [x] 在通用回调内处理异常，验证失败后的服务可用性。

**原问题：** 路径解码和页面模板读取可能抛出异常；`/bad%`、模板缺失等情况会让异常逸出事件循环。

**当前实现：** `GenericCallback()` 声明为 `noexcept`；读取 URI 和路径时先判空，缺失时返回 400；仅将路径解码的 `std::invalid_argument` 转为 400，其他未处理的业务异常由最外层 `catch (...)` 转为通用 500。

**已有验收：** `Returns400ForInvalidPercentEncodingAndContinuesServingRequests` 验证非法百分号编码返回 400，后续请求仍成功；模板缺失、目录占位和不可读测试验证返回 500，并在资源恢复后继续响应。权限用例在当前用户能绕过权限限制时可能跳过。

异常日志仍列入日志接入工作，不影响此项回调边界修复的完成状态。

修复提交：`3523419`。

### 1.3 上传文件名与存储边界

- [x] 在构造目标路径前校验解码后的文件名。

**原问题：** `Upload()` 直接拼接 Base64 解码结果。上传 `../escaped.txt` 曾返回 201，并把文件写到存储目录之外，随后下载返回 500。

**当前实现：** 解码后调用 `isValidFileName()`，校验通过后才构造路径和写入文件：

- 名称不能为空，也不能为 `.` 或 `..`。
- 不允许 `/` 和 NUL。
- 长度限制为 1～255 字节；255 字节是当前应用上限。
- 使用 UTF8-CPP 的 `utf8::is_valid()` 校验 UTF-8，作为文件名协议约束。
- 服务端仅运行于 Linux，允许反斜杠和除 NUL 外符合 UTF-8 的控制字符。

**已有验收：** 非法名称、路径逃逸、NUL、非法 UTF-8、超长名称均被拒绝；失败请求不创建文件、不改变元数据，也不覆盖已有文件。两种存储策略均覆盖合法名称、255 字节边界、反斜杠和控制字符的上传下载，另有重建 Service 后的元数据恢复测试。

严格 Base64 格式校验仍是独立待办，不计入本项完成范围。

修复提交：`ad8c587`。

### 1.4 两种存储目录相同

- [ ] 校验目录配置，明确存储类型判定所依赖的运行约束。

**问题：** `Config::readConfig()` 允许普通和压缩目录相同。`Download()` 优先按普通存储解释该目录中的文件，压缩内容会被当作原始内容发送。原隔离验证上传 32768 字节，下载返回 200，但正文只有 122 字节的压缩数据。

**处理方向：** 当前通过目录推导存储类型，需要保证两种目录可以明确区分；校验应考虑路径标准化和末尾分隔符，并明确指向同一目录的符号链接等别名如何处理。还需明确运行期间目录是否允许变化，配置重载问题见第 3 节。

**验收条件：**

- 相同目录及标准化后相同的目录配置被拒绝，不产生可运行的歧义配置。
- 配置加载失败时保留原有效配置。
- 合法的不同目录下，两种策略仍能完整上传下载，压缩文件返回原始字节。

### 1.5 下载路由与固定路由冲突

- [ ] 调整路由匹配，并明确下载前缀的配置规则。

**问题：** `GenericCallback()` 使用子串匹配，并先判断下载路由。配置允许下载前缀 `/`，此时首页被分发到下载处理并返回 404，上传被分发到下载处理并返回 405。

**处理方向：** 精确匹配 `/`、`/upload` 等固定路由；下载路由按路径前缀匹配，避免任意位置包含前缀就命中。明确 `/` 以及与现有、计划中的固定路由冲突的下载前缀是否允许，不合法的配置在加载阶段拒绝。统一路由路径解析，继续保证 URL 只解码一次。

**验收条件：**

- 首页和上传请求按约定进入对应处理函数。
- 覆盖默认前缀、自定义前缀、根前缀和固定路由冲突组合。
- 路径中间包含下载前缀的未知路径不被误判。
- 中文、空格、加号及字面 `%2F` 文件名仍能按正确的解码规则下载。

### 1.6 浏览器上传地址

- [ ] 页面使用同源相对地址上传，并完成浏览器验收。

**问题：** 页面通过 `{{BACKEND_URL}}` 使用配置 IP 拼接上传地址。浏览器通过 `localhost` 打开页面、服务配置为 `127.0.0.1` 时，上传会成为跨源请求，当前没有配套处理。这是原审查的代码检查结论，尚未做浏览器实测。

**处理方向：** 按开发计划使用同源相对地址 `/upload`；同步调整页面模板、后端占位符处理和相关测试。

**验收条件：** 分别通过 `localhost`、`127.0.0.1` 访问服务，完成普通和压缩文件的上传、列表展示、下载；上传请求始终发往当前页面所属的源。

## 3. 第一版必需工作与数据约束

除原审查第 4～6 项外，继续跟踪以下工作。

- [ ] **上传大小限制。** 在 HTTP 接收层限制正文大小，并在业务层分配内存前检查实际长度。覆盖边界、超限返回 413、失败后无新文件和元数据变化；继续允许零字节文件。
- [ ] **读取与解压大小限制。** 限制磁盘内容读取和解压后的内存占用；解压限制需要在处理过程中生效，避免完整分配后才检查。
- [ ] **应用入口与首次启动。** 当前 `main()` 仍只读取和输出配置。接入配置与日志初始化、数据目录和元数据父目录准备；仅在元数据文件缺失时创建 `[]`，随后构造 Service 并运行。已有元数据损坏时应报告错误，不覆盖历史数据。
- [ ] **应用侧 dlog 接入。** 记录启动、上传、下载、异常和关闭；补充回调中原始异常及上传失败清理错误的记录，客户端继续获得简洁错误响应。
- [ ] **正常停止。** 处理 SIGINT/SIGTERM，停止接收新请求，明确在途请求的收尾方式，退出事件循环并完成资源释放和日志刷新。
- [ ] **压缩数据完整性。** 原隔离验证中，压缩文件被截断为空后仍返回 200 空正文。需要在工具层识别损坏并让下载明确失败，同时区分合法零字节原文，避免把损坏数据当作成功结果。
- [ ] **配置重载策略。** Service 保存部分配置快照，其他处理仍读取全局 Config。原隔离验证中，运行时重载下载前缀后，上传返回的新 URL 会 404。明确第一版是否禁止运行中重载；若支持，需让路由、元数据 URL 和目录判定保持一致。重启时变更存储目录或前缀对历史数据的影响也需说明。
- [ ] **外部文件修改约束。** 明确数据文件是否允许被外部进程修改、删除或替换。若允许，补齐元数据、大小和 ETag 的同步规则；若暂不支持，在运行约束中写清楚。

## 4. 可后续安排的能力

- [ ] **严格 Base64 校验。** 当前 cpp-base64 可接受部分缺少填充或包含非法字符的输入。若协议要求标准格式，在编解码工具层统一提供严格校验，由 Upload 调用；不要与已完成的文件名校验混为一项。
- [ ] **HTTP 方法与缓存语义。** 补充 HEAD、条件请求和缓存行为。当前成功下载统一返回完整正文和 200，ETag 仅用于提供版本标识。
- [ ] **Range / If-Range。** 实现实际区间处理后再返回 206，并声明相应能力；当前不声明 `Accept-Ranges: bytes`。
- [ ] **大文件与流式传输。** 评估普通文件直接发送、压缩文件流式解压和分块发送，明确文件描述符所有权及发送生命周期。
- [ ] **业务并发。** 引入并发前补齐文件排他创建，避免检查冲突后目标路径被其他写入占用；明确并发删除、替换和下载的行为。
- [ ] **元数据存储优化。** 当前启动时全量加载，修改后同步持久化整张表；后续按数据规模评估增量持久化和其他存储方案。
- [ ] **独立 `/files` 接口。** 计划中保留 JSON 列表接口，当前由 `ShowFileList()` 直接渲染页面。确定第一版是否提供，并统一协议、文档和测试。

## 5. 已有设计基础

对照原审查使用的 [参考 Service 实现](https://github.com/youngyangyang04/Kama-AsynLogSystem-CloudStorage/blob/main/src/server/Service.hpp)，当前实现已经具备以下基础，后续修改应保留对应行为：

- libevent 资源按依赖顺序释放，先释放 HTTP 对象，再释放事件循环。
- Service 拥有自己的 DataManager，构造时加载持久化元数据。
- 上传检查冲突，元数据保存失败时回滚内存状态，并尝试清理本次上传文件。
- 列表文件名经过 HTML 转义，下载链接及响应文件名按用途编码。
- 下载缺失元数据时立即返回 404，使用元数据记录的磁盘路径定位文件。
- 压缩文件在内存中解压，不创建可能覆盖普通文件的解压临时文件。
- 未实现区间下载时返回完整 200，避免没有实际区间内容的假 206。

下一步优先解决第 4 项存储目录歧义，再处理路由与页面地址，随后完成大小限制、应用启动、日志和正常停止的闭环验收。

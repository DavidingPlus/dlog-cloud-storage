更新日期：2026-10-30。

当前设计的主干合理：单事件循环处理请求，同步读写文件，使用内存元数据表并持久化到 JSON，符合 Linux 服务端第一版小文件存储的目标。主要路径已有真实 HTTP 测试，第一版重点是补齐大小限制、应用启动、日志、正常停止和浏览器操作的闭环。

## 运行约定与范围

- `server.conf` 由维护者编写并保证正确、规范：两种存储目录指向不同位置，下载前缀与固定路由不冲突。配置仅在启动阶段读取，运行期间不修改或重载；不再增加错误配置、目录别名或热重载的防御实现及组合测试。
- 第一版使用单进程、单个 HTTP 事件循环处理小文件，数据文件和元数据由服务管理，不支持外部进程修改、删除或替换，也不实现自动同步。
- 重启后应沿用原存储目录和下载前缀。元数据保存了文件绝对路径和下载 URL，更改配置不会自动迁移历史文件或重写历史记录；迁移由维护者另行处理。
- 上述约定不适用于客户端请求。上传参数、文件名、请求大小、URL 编解码及实际读写失败仍需正确处理。

保留原审查的六项编号：第 1～3 项和第 5 项已完成，第 4 项由配置约定保证，第 6 项已修复并通过自动化测试，实际浏览器验收仍待完成。已有基础校验和测试保留，不继续扩展错误配置的覆盖范围。

### 1.1 默认存储目录末尾分隔符

- [x] 修复目录比较并增加回归测试。

**原问题：** `Download()` 直接比较配置目录和元数据文件的父目录。默认目录保留末尾 `/`，导致比较不相等，两种策略均出现上传 201、下载 500。

**当前实现：** 将配置目录与文件名组合，调用 `lexically_normal()` 后与元数据中的完整文件路径比较，兼容末尾分隔符。

**已有验收：** `DownloadsWithTrailingSeparatorsInConfiguredStorageDirectories` 覆盖带末尾 `/` 的相对、绝对目录，以及普通、压缩两种策略；上传后下载内容一致，重建 Service 后仍可下载。该测试覆盖默认配置的路径写法，尚不能代替默认配置下的完整应用启动验收。

修复提交：`fc8c5bd`。

### 1.2 请求回调异常边界

- [x] 在通用回调内处理异常，验证失败后的服务可用性。

**原问题：** 路径解码和页面模板读取可能抛出异常；`/bad%`、模板缺失等情况会让异常逸出事件循环。

**当前实现：** `GenericCallback()` 声明为 `noexcept`；读取 URI 和路径时先判空，缺失时返回 400；仅将路径解码的 `std::invalid_argument` 转为 400，其他未处理的业务异常由最外层 `catch (...)` 转为通用 500。

**已有验收：** `Returns400ForInvalidPercentEncodingAndContinuesServingRequests` 验证非法百分号编码返回 400，后续请求仍成功；模板缺失、目录占位和不可读测试验证返回 500，并在资源恢复后继续响应。权限用例在当前用户能绕过权限限制时可能跳过。

异常日志仍列入日志接入工作，不影响此项回调边界修复的完成状态。

修复提交：`3523419`。

### 1.3 上传文件名与存储边界

- [x] 在构造目标路径前校验解码后的文件名。

**原问题：** `Upload()` 直接拼接 Base64 解码结果。上传 `../escaped.txt` 曾返回 201，并把文件写到存储目录之外，随后下载返回 500。

**当前实现：** 解码后调用 `isValidFileName()`，校验通过后才构造路径和写入文件：

- 名称不能为空，也不能为 `.` 或 `..`。
- 不允许 `/` 和 NUL。
- 长度限制为 1～255 字节；255 字节是当前应用上限。
- 使用 UTF8-CPP 的 `utf8::is_valid()` 校验 UTF-8，作为文件名协议约束。
- 服务端仅运行于 Linux，允许反斜杠和除 NUL 外符合 UTF-8 的控制字符。

**已有验收：** 非法名称、路径逃逸、NUL、非法 UTF-8、超长名称均被拒绝；失败请求不创建文件、不改变元数据，也不覆盖已有文件。两种存储策略均覆盖合法名称、255 字节边界、反斜杠和控制字符的上传下载，另有重建 Service 后的元数据恢复测试。

文件名安全检查已完成。Base64 沿用 cpp-base64 的解码规则，解码失败返回 400；拒绝所有非标准编码写法仅作为可选协议增强。

修复提交：`ad8c587`。

### 1.5 下载路由前缀匹配

- [x] 下载请求仅匹配路径起始位置的配置前缀。

**原问题：** `GenericCallback()` 使用子串匹配，`POST /other/download/a.txt` 这样的未知路径会误入下载处理并返回 405。

**当前实现：** 使用 `0 == requestPath.find(service->m_downloadPrefix)` 判断下载前缀是否位于路径开头，避免把路径中间包含前缀的未知路由分发到下载处理。保留路由顺序、配置规则和 URL 解码流程。

以下载前缀 `/download/` 为例：

| 请求 | 处理行为 |
| --- | --- |
| `GET /download/a.txt` | 进入下载处理 |
| `GET /other/download/a.txt` | 作为未知路由返回 404 |
| `POST /other/download/a.txt` | 作为未知路由返回 404 |

**已有验收：** `MatchesDownloadPrefixesOnlyAtTheStartOfThePath` 覆盖默认 `/download/` 和自定义 `/files/` 前缀：正确前缀的 POST 仍进入下载处理并返回 405，前缀仅出现在路径中间的 GET、POST 均返回 404。既有测试继续覆盖正常上传下载和中文、空格、加号及字面 `%2F` 文件名。

### 1.6 浏览器上传地址

- [x] 页面使用同源相对地址上传，清理后端地址注入并补充自动化测试。
- [ ] 完成实际浏览器及反向代理联调验收。

**原问题：** 页面通过 `{{BACKEND_URL}}` 使用配置 IP 拼接上传地址。浏览器通过 `localhost` 打开页面、服务配置为 `127.0.0.1` 时，上传会成为跨源请求；通过域名或使用不同协议、端口的反向代理访问时也会出现相同限制。

**当前实现：** 页面使用 `fetch('/upload', ...)`，沿用当前页面的协议、主机和端口；删除 `backendUrl`、后端的地址占位符替换，以及未使用且依赖旧地址的下载辅助函数。列表中的下载链接继续使用已有的相对路径。反向代理需将 `/upload` 和配置的下载路径转发到同一个服务。

**已有验收：**

- `UploadsAndDownloadsWithDifferentHostHeaders` 使用真实本地 HTTP，覆盖 IP、localhost、域名及 HTTPS 代理对外地址对应的 Host/Origin；验证两种策略上传、列表展示和二进制内容下载。测试连接本身是本地 HTTP，没有建立实际 HTTPS 代理。
- `test/server/web/upload_test.js` 用 Node.js 直接执行真实模板中的上传脚本，模拟 DOM 和 fetch，覆盖四种页面地址与两种策略共 8 个用例。检查实际传给 fetch 的地址解析后与页面同源、路径为 `/upload`，同时验证中文文件名编码、存储策略、文件正文和成功后的刷新。该测试无需第三方依赖，不等同于真实浏览器的跨源与代理联调。
- 2026-10-30 执行 `rtk xmake test -y tests/server` 和 `rtk node test/server/web/upload_test.js`：185 项服务端测试及 8 项页面脚本测试全部通过。用修复前的固定后端地址运行脚本测试时，8 项均按预期失败。

**剩余验收：** 在实际浏览器中通过 localhost、IP 和反向代理访问，确认两种策略的上传、列表及下载可用，请求始终发往当前页面所属的源。

## 4. 建议补充的基本错误处理

- [ ] **压缩数据异常识别。** 原隔离验证中，非空压缩文件被截断为空后仍返回 200 空正文。建议结合元数据与解压结果识别明显截断或解压失败，同时保留合法空文件语义。优先级低于应用运行闭环，不扩展为全面完整性校验或自动恢复系统。

## 5. 可选增强

以下内容按实际需求选择，不作为第一版待完成清单，也不在代码中逐处保留 TODO。

- **严格 Base64 格式校验**：仅在协议要求拒绝全部非标准写法时增加，不能替代解码后的文件名检查。
- **HEAD、条件请求和缓存**：当前下载返回完整正文和 200，ETag 仅提供版本标识。
- **Range / If-Range**：实现实际区间处理后再返回 206；当前不声明 `Accept-Ranges: bytes`。
- **大文件与流式传输、解压过程内存限额**：需要支持更大文件或异常数据防护时再设计发送生命周期和解压上限。
- **业务并发**：引入工作线程或多进程写入时，再补齐文件排他创建及并发操作约束。
- **元数据存储优化**：按数据规模决定是否替换当前内存表与 JSON 全量保存方案。
- **独立 `/files` JSON 接口**：现有页面直接渲染列表已满足第一版，不要求新增接口。

## 6. 已有设计基础

对照原审查使用的 [参考 Service 实现](https://github.com/youngyangyang04/Kama-AsynLogSystem-CloudStorage/blob/main/src/server/Service.hpp)，当前实现已经具备以下基础，后续修改应保留对应行为：

- libevent 资源按依赖顺序释放，先释放 HTTP 对象，再释放事件循环。
- Service 拥有自己的 DataManager，构造时加载持久化元数据。
- 上传检查冲突，元数据保存失败时回滚内存状态，并尝试清理本次上传文件。
- 列表文件名经过 HTML 转义，下载链接及响应文件名按用途编码。
- 下载缺失元数据时立即返回 404，使用元数据记录的磁盘路径定位文件。
- 压缩文件在内存中解压，不创建可能覆盖普通文件的解压临时文件。
- 未实现区间下载时返回完整 200，避免没有实际区间内容的假 206。
